# 设计：v2.5.2 git 自循环任务执行体（定稿——2026-08-14）

> 调研：CA 875 行报告（task-loop.md）+ 我补充（Loop Engineering/编排器/选型）
> 用户洞察：自循环=完整任务执行体（非失败自愈）——四类任务源统一进循环
> 选型决策：不用 Temporal（单机分钟级任务——简单队列+状态机够——less magic）

## 一、选型定稿

| 组件 | 选型 | 原因 |
|------|------|------|
| 任务存储 | Git Issue（docs/issues/）| 零基础设施/代码关联/人类可读——<200 任务够 |
| 执行状态 | 轻量状态机（文件/内存）| 单机——不需要 Temporal 事件历史 |
| 任务编排 | 简单队列 + 状态机 | Reddit 共识——less magic more control |
| 外部接入 | REST API（HTTP）| IDE/智能体提交任务进循环——A2A 以后再说 |
| 定时 | cron（Hermes）触发进循环 | 定时任务失败→挂单重派（替代回放——效果接近简单 100 倍）|
| 状态模型 | open→queued→running→fixing→verified→done（+retry/escalated/dead）| 对齐 Linear/GitHub |
| 持久化 | 任务定义在 git——执行状态在 issue 文件 | 重启不丢（git 就是持久化）|

## 三、实施（按序——P0 起步）

### P0: 任务执行体骨架
```
1. 状态机扩展（issue_tracker.go）: open/fixing → +queued/running/verified/done/dead
2. 调度器（新——scheduler.go）——异步派单（核心——防卡死靠架构不靠监控）:
   - 轮询扫描 docs/issues/（open/queued——按优先级排序先派高优先）
   - 派单（启动 worker 子进程——不等待——立即继续扫下一个）
   - 永不等（调度器永不卡——worker 卡了只影响自己）
   - 冷却（失败 ≥30s 重派——对齐调研 DLQ）
   - issue 锁（派单前标记 running——状态机即锁——其他轮次跳过防抢）
3. worker（新——worker.go——独立进程跑 CA）:
   - 跑 zerg-agent -issue <path>
   - 更新 issue 状态（自己汇报——不依赖调度器等）
   - 完成→verified / 失败→failed+挂单重派
4. 任务入口统一（新——entry.go）:
   - 四类源统一生成 TaskSpec（task/type/priority/repo）→ 写 docs/issues/
   - 去重（task-hash 已有——完善）
   - 优先级字段（high/normal/low——调度器排序）
5. 并发配置（config/workers.yaml——设备感知）:
   - mini1: max_workers=1（16G 单线）
   - X3: max_workers=3（122G 多路——每 worker 显存 ~30G 防 OOM）
   - local: max_workers=2（M4 Max）
   - 调度器按配置派——不超配（防资源争抢）
6. commit 时机（生命周期关键点）:
   - 新任务挂单 / 状态变更 / 完成结论 → 各 commit 一次（git 全程留痕）
```

### P1: 外部接入（REST API + 可发现性）
```
- HTTP 服务（调度器内嵌——不额外进程）
- POST /task（提交任务——进循环）——GET /task/{id}（查状态）
- 鉴权: 配置文件预置 token 列表（~/.zerg/tokens.yaml——每调用方一个）
  - 外部调 POST /task 带 token——撤销=删 token
  - 不做 OAuth（本地单机——够用）
- 可发现性（用户定——别人怎么知道怎么调）:
  - GET /docs（OpenAPI 文档——人类浏览器看——参数/示例/一键尝试）
  - GET /capabilities（能力清单——机器可读 JSON——Agent 读取匹配）
  - 文档含: curl + Python 示例——真实用例 2-3 个
  - 核心理念: 接口自带"菜单"——人类看文档/Agent 读清单——双方都能"读→匹配→调"
- 外部 IDE/智能体 → 提交任务 → 进 git 任务体
```

### P2: 定时接入（cron → 进循环）
```
- Hermes cron → 触发"提交定时任务"（写 issue）→ 调度器派单
- 定时任务失败 → 挂单重派（错误自愈）
```

### P3: 验收器 + 监控
```
- 验收标准（任务类型×验证方式——TaskSpec.type）:
  - code: 测试跑通（go test）/构建通过
  - report: 产物文件存在+非空
  - research: 报告文件存在（人工抽检）
  - fix: 原失败复现消失（测试过）
  → confirmed/rejected
- 面板（open/queued/running/fixing/verified/done 计数——失败类型分布）
- 告警（连续失败≥3→P1 / dead 积压>10→P2）
```

## 六、防卡死（生命体态检测——用户设计 + 业界验证）

```
用户洞察: 卡死 ≠ 超时/轮数多——是"彻底没有运动痕迹"（死寂）
  - CPU/GPU 在算/进程在/磁盘在写/日志在记 = 活着（在动——即使慢/重试/死循环）→ 不是卡死
  - 全部死寂（零运动痕迹持续） = 卡死 → 才处置
业界验证: OpenHands Stuck Detector / K8s Liveness / Zylos 双层心跳——同思路
  - "卡死不是超时——是还在动但没进展"
  - L1 进程心跳 / L2 活动进展 / L3 语义模式——三层（不设时间限制）

三层生命体态检测（定稿）:
  L1 进程心跳（还活着吗）: CPU 使用率/进程状态/磁盘 IO/日志事件——多维信号
    ——任一活跃 = 活着
  L2 活动进展（在生产性工作吗）: Progress Metric（完成步骤/产物增长）
    ——有进展 = 在干活（即使慢）
  L3 语义模式（陷入循环/卡死吗）: 模式匹配（重复动作/交替/独白——OpenHands）
    ——重复模式 = 卡死信号（也是"体态"——非时间）

判定逻辑（用户核心——只处理死寂）:
  任何生命信号活跃 → 活着（不干预——不设最大轮数/时间）
  全部死寂（L1 零信号）持续 → 卡死 → kill + 挂单重派
  L2 无进展 + L3 重复模式 → 死循环信号 → 反馈/重派（非时间判断）

原则（用户哲学）:
  - 不限制 agent（100 轮自由——超时不是机制——是保险丝兜底）
  - 系统只做"生命体态监护"（看动不动——不规定干多久）
  - 尊重硬件（并发按设备能力——配置）
```

## 七、风险

```
- 调度器单点（本地——可接受——重启恢复）
- 并发污染（单 agent 串行——防）
- issue 文件膨胀（定期归档 dead——git 历史保留）
- 外部接入安全（鉴权——复用网关 token）
```
