Zerg has exactly one face to the outside: the **command line**. Every capability lives in the command tree, shaped as

```text
zerg <object> <action> [arguments] [flags]
```

Objects and actions go at most three levels deep. There is one rule of usage: **type commands, do not glue scripts together** — the existing scripts and HTTP surfaces are all taken in as internal implementations of commands; the command line is the only entry point.

---

## 0. Note for this build · one behaviour change **external scripts can observe**

For `--json` **with the flag but without fields** (e.g. `zerg gate run --json`), the exit code moves from `1` to **`2`** (usage error).

* **Why**: the exit-code table (`zerg help exit-codes`, the single source of truth) says "usage error = `2`". The old implementation returned `1` here, out of step with its own table — a case of "the spec itself was wrong", so **the table wins** (one of the exceptions to the compatibility promise: security / unspecified behaviour / spec error).
* **What changes**: only the **exit code** of this one cell. stdout is still **0 bytes** (the dangerous-action tier emits a machine-readable error envelope), and the field list still goes to stderr — the prompt face is unchanged to the byte.
* **Who is hit**: scripts/CI that test `rc == 1` to mean "arguments incomplete". Test `rc == 2` instead (or use the semantic names from `zerg help exit-codes`; do not copy numbers into your predicates).
* **No silent change**: this is also recorded in `CHANGELOG.md`; the matrix (`core/cmd/zerg/testdata/cli-matrix.json`) was **re-frozen in the same commit**, 26 cells `want_rc` `1 → 2`.

## 1. Where to find the command you need

The help face is itself made of commands — ask it first:

| Command | What it gives you |
|---|---|
| `zerg help` | the **usage string** of every command (one per line, verbatim from the command tree) |
| `zerg help <topic>` | a single topic page (the topic table lives in the command tree) |
| `zerg help dangerous` | the list of dangerous actions + the shape of the three-state confirmation |
| `zerg help exit-codes` | the exit-code table (single source of truth) |
| `zerg help config` | the configuration precedence chain |
| `zerg help credentials` | tokens and credentials |
| `zerg version` | one-line identity (component · version · code sha · build time) |

## 3. Conventions to know before writing a command

- **Dry run first**: for any command that changes state, start with `--dry-run` — it only produces a **plan artifact** and leaves system state byte-for-byte unchanged (zero side effects).
- **Three-state confirmation for dangerous actions**: `--dry-run` (zero side effects) · `--confirm=<target>` (the value must match the target **verbatim**; a wrong value is a refusal, not "treated as absent") · `--yes` (the third tier requires `--confirm` and `--yes` together).
- **Non-interactive is fail-closed**: with no TTY there are **no prompts at all**, and a missing confirmation is always a refusal to execute (nothing "waits and asks").
- **Machine face**: `--json <fields>` requires a comma-separated field list — omit it and you get exit code 1, the field list on stderr and zero bytes on stdout; `--plain` is the default when not a TTY (line-oriented output).
- **Rejection rules** — requesting an unknown field ⇒ exit code `2` + every legal field listed; `--json` given without any field ⇒ exit code `2` + the full field list on stderr (the schema is self-describing); `--schema` with an unrecognised major ⇒ exit code `2`; `--json '*'` **does not exist** — the value is a comma-separated list of field names.

  > 中文原句（真源逐字 · [CLI.zh-CN.md](CLI.zh-CN.md)）：**拒绝规则**：请求未知字段 ⇒ 退码 `2` + 列全部合法字段；`--json` 不给字段 ⇒ 退码 `2` + stderr 列全部字段（schema 自描述）；`--schema` 主号不认 ⇒ 退码 `2`；`--json '*'` **不存在** —— 要的是逗号分隔的字段名。
- **Exit codes**: 0 success · 1 general failure · 2 usage error / no verdict · 4 unauthenticated · 8 something is BLOCKED; see `zerg help exit-codes` for the per-code table.
- **Credentials**: the token is read only from an environment variable or a credentials file, and **never goes into argv**.

## 4. Dangerous actions

Actions that change machine state (loading/unloading models, starting or stopping processes, swapping artifacts, deleting tasks …) are registered separately in the command tree as **dangerous actions**, each carrying "tier · three states · what `--confirm` targets · what it touches". Part of them are **not open yet**: those refuse to execute on a real run (exit code 2 = no verdict), and only the `--dry-run` plan face is available.

See `zerg help dangerous` for the per-command list and tiers, or the generated region in section 2.
