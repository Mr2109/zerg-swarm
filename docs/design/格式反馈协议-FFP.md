# 工具调用格式反馈协议（FFP）

> **这是什么**：FFP（Format Feedback Protocol，**工具调用格式反馈协议**）是虫族在**工具调用格式出错**时，回给模型的一段结构化“教学文本”，而不是一句干巴巴的报错。
>
> **解决什么问题**：本地模型发出的工具调用经常格式跑偏——空参数、被截断、JSON 语法错。如果系统只回一句“执行失败”，模型无信息可学，只会**原样重发**，重试几轮后任务失败。FFP 把“每一轮里唯一一次教学机会”变成一次可执行的纠错。
>
> **谁该读**：给 LLM Agent 写工具循环 / 防呆兜底的开发者；接入自研或本地模型的工程师；以及认同下面这条理念的人。

> **设计理念：没有弱模型，只有不完善的系统。**
> 模型任务失败、格式跑偏、工具调用异常——一律先归因**系统**（提示设计、解析层、防呆兜底、反馈协议），
> 而不是甩锅给模型。本文是这条理念在“工具调用格式”这一层上的完整落地。

---

## 一、问题：所谓“弱模型”，多半是系统没把话说清楚

### 1.1 一次真实的失败现场

某次验收任务，两次运行失败，模式完全一致：

1. 模型（`example-35b`）发出一个 `bash` 工具调用，`command` 字段为空；
2. 系统回馈一句话：`bash 执行失败: bash: 命令参数为空`；
3. 模型从反馈里**得不到任何可学信息** → 原样重发 → 还是空 → 重试 3 次 → 判定“无进展” → 任务 `failed`。

**根因不在模型“发错”，而在系统把唯一一次教学机会浪费成了一句空泛的错误文本。**

模型每一轮**唯一的输入**就是反馈文本。格式错误发生时，只有系统同时掌握三方信息：

- **模型原始输出**（那段格式坏掉的调用片段）
- **parser 卡在哪**（解析器在哪一步失败、期望什么）
- **期望的 schema**（正确形态长什么样）

不反馈，这三样就只能烂在日志里，模型永远只能瞎猜。

### 1.2 关键区分：格式错误 ≠ 执行失败

| | 定义 | 例子 | 模型该怎么理解 |
|---|---|---|---|
| **执行失败** | 调用**被正确解析并执行**，但运行结果失败 | `bash` 跑了，退出码 ≠ 0 | “我的命令逻辑不对” |
| **格式错误** | 调用**根本没被执行**，卡在解析/校验层 | `bash.command` 为空、JSON 语法错 | “我这次调用没写对格式” |

把两者都塞进“执行失败”通道，会让模型**误判为“逻辑失败”**，于是去改逻辑——而它真正该改的是格式。这是死循环的第一推动力。

### 1.3 现状诊断（逐条对照代码）

| # | 环节 | 旧行为 | 问题 |
|---|---|---|---|
| P1 | 工具错误通道 | `bash.command == ""` → 返回 `Error: "命令参数为空"` | 走的是普通工具 Error——模型以为是“逻辑失败” |
| P2 | 反馈文本 | 一句干错误串，无原文、无期望、无示例 | **零教学信息**——模型只能原样重试（实测死循环） |
| P3 | 重试语义 | 对同一个坏调用做退避重试 | 格式错、重试同 payload **必然再错**——白白烧 3 轮才判无进展 |
| P4 | 解析层畸形容忍 | 适配器能静默修掉的小畸形就修 | 缺一个“修不了 → 结构化反馈”的出口——修不了的直接掉进 P1 |
| P5 | 错误样本沉淀 | 日志有记录，但无分类、无指纹 | 无法驱动上游（schema / 工具描述 / 适配器）改进——反馈系统不会自进化 |

## 二、设计原则：系统断言 + 可执行反馈

### 2.1 系统断言（system assertion）

运行时异常应该由**系统**在**首行**给出确定性定性，早于任何模型解读。这条原则在虫族里不是新东西——`bash` 的**执行错误**早就这么做了：

```
⚠️ exit 1
[guide] 命令退出码非 0——看输出定位；不要原样重发……
```

首行定性（`⚠️`）+ 分类引导（`[guide]`）+ 超长输出落盘续读。**格式错误此前还没有同等待遇**——FFP 就是补齐这一层。

### 2.2 可执行反馈，而非不透明错误码

把工具调用错误**当作提示工程来写**：错误响应应当是“具体、可行动的改进指引”，而不是不透明的错误码或堆栈。这不是虫族的独家发明——业界对“执行失败反馈”的共识与之逐条同构。Anthropic 的工程文章《Writing effective tools for agents》原文即：

> “prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks.”

FFP 就是把这条原则**系统化**：每次格式错误，都稳定产出同一种结构化教学文本。

### 2.3 三条铁律

1. **首行定性**——模型第一眼就知道“这是格式错，不是执行失败，别原样重发”。
2. **确定性分类**——分类由 parser 逐条匹配得出，不靠模型自我解读（模型自查格式正是它最不擅长的事）。
3. **给可抄样例**——本地模型最缺的不是“道理”，而是一行**能直接抄的最小合法形态**。

## 三、协议细节

### 3.1 触发条件

FFP 只在**格式层**触发，不动执行层：

- 适配器**修不了**的畸形（见 3.6）；
- parser / 执行入口发现**格式级**故障——例如必填字段缺失、字段类型错、整段调用为空、名字不在工具清单里。

**合法调用零变化**；**真执行失败**（exit ≠ 0）仍走原有的 `⚠️ exit N` 断言通道——FFP 只补“执行前”的那一层。

### 3.2 文本结构（坏调用 → 结构化教学文本）

`bash` 空 `command` 的实测输出：

```
⚠️ 工具调用格式错误(系统断言——非执行失败——请勿原样重发)

[格式分类] 参数缺失: bash.command
[你上一条发送] {"command":""}
[parser 期望] 字段 command:string 非空(trim 后)——为必填字段
[最小合法示例] {"command": "ls -la"}
[guide] 命令字段不能为空——先想好要执行什么,再发完整 JSON 工具调用;命令本身勿用引号包裹 JSON
```

各字段职责：

| 字段 | 给模型的什么 | 说明 |
|---|---|---|
| 首行 | **定性** | 与 `bash ⚠️ exit N` 同构的系统断言；明确“非执行失败”“勿原样重发” |
| `[格式分类]` | **确定性判定** | parser 逐条匹配，不是模型解读 |
| `[你上一条发送]` | **它唯一缺的信息** | 模型自己实际发了什么（内部做窗口化，见 3.4） |
| `[parser 期望]` | **缺什么 / 要什么** | 点名到具体字段与类型 |
| `[最小合法示例]` | **可抄样例** | 一行就能照抄的最小合法 JSON |
| `[guide]` | **下一步引导** | 一条正向动作指令 |

生成这段文本的代码非常薄——一个独立的小包，方法干脆利落地拼装：

```go
// core/internal/ffp/ffp.go
const Prefix = "⚠️ 工具调用格式错误(系统断言——非执行失败——请勿原样重发)"

func Is(msg string) bool  // 是否 FFP 文本（首行精确匹配）
func In(msg string) bool  // 容忍 "工具名: " 前缀的包含判定
func Echo(raw string, headN int) string
func Build(kind, sent, expected, example, guide string) string
```

`Build` 不做任何智能判断——分类、回显、期望、示例都由**调用方确定性给出**。

### 3.3 错误分类表（确定性——系统匹配，不靠模型）

| 分类 | 判定特征（parser 层） | 引导要点 |
|---|---|---|
| 截断 | JSON/XML 未闭合、意外 EOF、长度断点 | “输出被截断——拆小请求 / 减少内容；勿重发同长度” |
| 参数缺失 | 必填字段不存在，或为空串 | 点名字段 + 给最小示例 |
| 类型错误 | 期望 `string` 却给了数字/对象等 | 点名字段与期望类型 |
| 非法 JSON/XML | 语法错、转义坏、多余尾字符 | 回显坏片段 + 完整示例 |
| 空调用 | 整段为空 / 仅空白 / 仅注释 | 引导先用 `tool_search` 或查工具 schema |
| 未知工具/字段 | 名字不在清单里 | 列出相近可用工具（`tool_search` 已覆盖，补一句引导） |
| **参数值语言不匹配** | 值含非 ASCII，而 schema 把该参数约定为英文枚举（`enum`）或 `"x-zerg-format": "ascii" / "id"` | 点名 工具.参数 + 列出英文枚举 + 给最小合法示例（**勿翻译成中文**） |
| **枚举值非法** | 值是 ASCII 但不在 `enum` 值域内 | 列出合法值域（`a \| b \| c`）+ 最小示例 |
| **日期格式非法** | `"x-zerg-format": "iso-date"` 而值非 `YYYY-MM-DD` | 给 ISO 8601 示例（`2026-09-11`） |

分类**只影响引导文案，不影响执行权**——所以即便分类偶有误判，代价也极低（见第五节）。

#### 3.3.1 参数值语言不匹配（多语言专项——2026-09-11）

**为什么单列一类**：MLCL / *Lost in Execution*（ACL 2026）的实证结论是——多语言场景下工具调用失败的主因**不是“模型看不懂语言”**，而是**把非英语 token 直接塞进参数值**（模型选对了工具、语义也对，却在执行接口上失配）。因此这类错误值得拥有**自己的分类与引导**：把 schema 里的接口约定（英文枚举 / ASCII / ISO 日期）讲清楚，而不是把提示词整体翻译一遍。

**触发与引导（实测形态）**：模型发 `todo` 且 `action=创建`，而 schema 声明 `enum: [create, update, list]`：

```
⚠️ 工具调用格式错误(系统断言——非执行失败——请勿原样重发)

[格式分类] 参数值语言不匹配: todo.action
[你上一条发送] 创建
[parser 期望] 枚举值（英文）: create | update | list
[最小合法示例] {"action": "create"}
[guide] 把该参数值改成上面「最小合法示例」的形式重发本工具调用——枚举/日期/ID 一律原样照抄，不要翻译成中文、不要加空格。
```

**防呆边界**（不误伤）：只认 schema **显式声明**的约定（`enum` / `x-zerg-format`）。未声明的参数一律放行——中文路径、中文查询词在本项目里是合法输入（如 `00 项目/模型类/报告.md`），不得拦截。

### 3.4 原文回显规则

- 回显模型原始调用片段时取**头 200 字符 + 尾 200 字符**，中间以 `[省略 N 字符]` 标注——与 `bash` 的溢出窗口 / 落盘同一思想，防爆上下文；
- 整段为空时回显 `<空/缺失>`；
- 超长场景可**全量落盘**，让模型用 `read` 续读；
- 回显前做**敏感扫描**（token / 密钥形态），确保不把凭据原文回灌给模型。

### 3.5 与工具循环的交互

FFP 不是终点，而是**回喂给模型**、改变它下一轮行为的一次“教学轮”。关键交互有三点：

1. **不包装成执行失败**。工具循环检测到 FFP 文本后**原样直通回喂**，不再加 `工具执行失败: …` 前缀——否则会与首行的“非执行失败”断言自相矛盾。回喂条目的状态标记为 `[格式反馈]`（而非 `[失败]`）。
   ```go
   // core/internal/loopcore/run.go（示意）
   if ffp.In(execErr.Error()) {
       content = e                       // 教学文本直通，不包装
   } else {
       content = fmt.Sprintf("工具执行失败: %s", e)
   }
   // 状态：ffp.In(...) → "[格式反馈]"，否则 → "[失败]"
   ```
2. **重试语义修正**。格式错误**不计入**普通退避重试（同 payload 必再错）；而是**单独计数**——“连续格式错 N 次”比吞掉整轮更能驱动收尾，避免无谓烧轮次。
3. **计数与升级**。同一格式错连续 2 次 → 反馈**升级**：附上该工具的完整 schema（从 `tools/<名>.md` 或参数定义拉取）。若整段 `<tool_call>` 连坏 3 次，则触发收尾引导（`bad_format` 退出）。

### 3.6 与适配器修复层的分工

解析层对“能修就修”与“修不了就教”有清晰分界：

- **能修的小畸形**（引号转义、缺闭合括号、多余空白）→ 适配器**静默修复**，不打扰模型；
- **修不了** → 走 FFP 反馈（本协议）；
- 修复动作**记入事件流**（修了什么 / 没修什么）——修复是**机械修复**，不是猜意图，杜绝“静默修错语义”。

## 四、实证与案例

### 4.1 回归样本：`bash` 空 `command`

上面 1.1 的实测坏样本已固化为回归用例。修复后，同一条空 `command` 调用产出的反馈包含：

- 首行系统断言；
- `[格式分类] 参数缺失: bash.command`（类型错时则是 `类型错误: bash.command(string)`）；
- `[最小合法示例] {"command": "ls -la"}`。

验收标准写得很直白：**旧式干错误文本（“命令参数为空”）必须消失**，且模型在坏调用后应**一轮自纠**（不再连空）。

### 4.2 各分类的修复前后

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `bash` 空 `command`（实测样本） | 干 error，死循环重试 | `⚠️` 断言 + 缺失点名 + `{"command": "ls -la"}` 示例 → 一轮自纠 |
| 工具调用截断（历史上一族反复出现的失败） | 解析失败后隐式重试 | “截断”分类 + 省略标注 + 落盘续读 |
| 引号转义坏（JSON 语法错） | 干 error | 坏片段回显 + 完整示例 |
| 适配器可修的小畸形 | 静默修 | 保持静默修 + 记事件流（行为不变） |
| 真执行失败（exit ≠ 0） | `bash ⚠️` 断言 | 不变——FFP 只补执行前的格式层 |

### 4.3 让反馈系统自进化

FFP 的价值不止于“这一轮纠错”，还在于把错误变成**可度量的资产**：

1. **格式错误指纹**——按「分类 × 工具 × 字段」计次，喂给循环守卫与事件流；某字段反复缺失，就说明是 **schema / 工具描述**的引导问题，驱动上游去修。
2. **回归样本集**——把真实坏调用入库，作为解析 + 反馈生成单测的回放素材。
3. **教学效果度量**——统计“同工具同格式错的二次发生率”（反馈后模型是否自纠），用真任务跑分验证 FFP 到底有没有用。把工具错误当**指标**驱动迭代，与业界做法一致。

## 五、如何扩展与注意事项

### 5.1 增加一种分类

1. 在 **parser / 执行入口**判定该格式故障属于确定性分类（对照 3.3 表）；
2. 调用 `ffp.Build(kind, sent, expected, example, guide)` 组装反馈——五个参数全部由调用方**确定给出**，不要把判断塞进 `Build`；
3. 补一条回归用例：命中该分类时，反馈须含断言首行、正确的 `[格式分类]`、以及可抄的最小示例；
4. 若涉及工具行为，同步更新 `tools/<名>.md` 履历与工具简介。

### 5.2 注意事项

- **回显可能又长又噪**。已用「头 200 + 尾 200 + 省略标注」+ 超长落盘控制；改动窗口时先想清楚本地模型的上下文预算。
- **模型可能把示例当字面照抄**。示例尽量带占位符，并在 `guide` 里提示“按你的场景改名 / 改值”。
- **分类误判成本低**。分类只影响引导文案、不影响执行权——所以宁可让它快速给出一个分类，也不要为了“绝对准确”而卡住反馈。
- **别把 FFP 包进“执行失败”**。任何在 FFP 文本外再加 `工具执行失败:` 前缀的地方，都会削弱首行断言的效力（3.5 第 1 点）。
- **敏感信息**。回显前必扫 token / 密钥形态；是否需要连路径、文件名一起打码，可视部署场景再收紧。

### 5.3 与“事前预防”的关系

格式错误有两派解法：

- **反馈（事后教学）**——FFP 这一层；
- **约束解码（事前预防）**——用 JSON schema / regex / grammar 在解码期引导生成，让格式错误**根本不可能发生**，例如 vLLM 的 structured outputs、llama.cpp 的 `--grammar`。

结构预防是终局方向，但它**不是 FFP 的替代**，而是并行互补。虫族有过教训：早期把模板与 grammar 混用曾引发**空参数根因冲突**，导致多轮重写——所以约束解码需要先解决“模板 × grammar”冲突，才能作为远期预防手段接入。当下的补层，就是 FFP：**不改变模型的解码过程，只保证一次格式错误必然换来一次可执行的纠错。**

---

**一句话总结**：格式错误是**执行前的系统层异常**，不是模型的“笨”。系统的责任，是在模型每一次犯错时，同时把它**发了什么、缺了什么、抄什么能过**——原原本本地告诉它。

## 与其它层的关系

- FFP 的定位未变：**工具调用格式出错时，回给模型的是结构化教学文本，而不是一句干巴巴的报错**——这是「没有弱模型，只有不完善的系统」最直接的落地之一。
- 现读一条相关边界：**控制层规则独立于模型侧**——那份规则文件（`rules.yaml`）是给「什么能执行」兜底的，**模型看不到、也改不了**它；FFP 负责把「怎么改」讲清楚，控制层负责「让不让做」。两层各管一段，不互相替代。
- 命令行面新增的 `zerg publish preflight` 与 `zerg publish run` 同样吃这套：计划件与确认态都走**人可读、模型可读**的显式输出，而不是靠猜。
